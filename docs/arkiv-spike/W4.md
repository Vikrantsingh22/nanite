# W4: schema and queries (Arkiv spike T0.3)

Script: `scripts/arkiv/w4-queries.ts` (stages: seed, queries, poison, lookalike, latency). Raw results: `docs/arkiv-spike/results/W4.json`. Chain: Rabdi, public RPC (no key). Writer = index 5 `0xC8568eacC33877B26CFdB1e9257478853D3e501C`, attacker = index 6 `0x79925Fd8DFb1b656025038fE46CDD412345919eC`. Ciphertext columns hold random bytes (no real mail).

## Headline
All of (a)-(g) work, builder and raw string, with correct results and correct ordering, on the existing `nanite.email.v0` schema without change. Poisoning is real: a naive query returns the attacker's rows (and puts them first). Pinning `$creator` removes them. **Every Nanite query must pin `$creator = addr(<Nanite writer>)`.** Typical read latency after receipt is 0.4-2 s.

## Seed (test 1)
One `executeBatch`, 12 creates, tx `0x7483dcb774f7e3973d9e1f2b06ddaa370ca22bd672a54793c44c8e4d1ecc32d4`, expiry 1 h. alex: 8 emails (4 otp, 4 conversation, threads thr-A x2, thr-B x2, 4 single otp threads), bob: 4 emails. receivedAt spread 10 min apart over 2 h. ownerId = fake `0x1111...1111`. senderHash = HMAC-SHA256(test secret, lowercased sender), 64 hex chars. Keys are in results/W4.json (`test: "seed"`).

## Final query patterns (verified)
Literal syntax gotchas: `addr(0x...)` and `key(0x...)` are UNQUOTED (`addr('0x..')` is rejected: "addr takes a 0x-prefixed address"; the note in sdk-notes.md and the placeholder in query.curl.sh are wrong on this). `str('..')` is quoted, `u64(n)` plain. ORDER BY is appended as `ORDER BY receivedAt:u64 DESC` (type suffix required for raw).

Prefix used everywhere (P): `arkiv.schema = str('nanite.email.v0') AND $creator = addr(0xC856...501C)`

| # | Purpose | Raw string (after P) | Builder | Result |
|---|---|---|---|---|
| a1 | inbox page 1 | `P AND agentId = str('alex...') ORDER BY receivedAt:u64 DESC`, limit 5 | `select(..).from(EmailSchema).createdBy(W).where(eq("agentId",A)).orderBy(desc("receivedAt")).limit(5)` | 5 rows, newest first, OK |
| a2 | page 2 (offset) | same, offset 5 | `.offset(5)` | 3 rows, OK |
| a3/a4 | page via $key cursor | `... ORDER BY $key:key ASC` then `... AND $key > key(0x<last>)` | `.orderBy(asc("$key"))` then `.where(eq(..), gt("$key", key(last)))` | 5 + 3 rows, no overlap, OK |
| b | only otp | `P AND agentId=.. AND type = str('otp')` | extra `eq("type","otp")` | 4 rows, OK |
| c | latest otp | b + limit 1, desc | `.limit(1)` | the newest otp, OK |
| d | time range | `P AND agentId=.. AND receivedAt >= u64(lo) AND receivedAt <= u64(hi)` | `between("receivedAt", u64(lo), u64(hi))` | 4 rows inclusive both ends, OK |
| e | thread | `P AND agentId=.. AND threadId = str('thr-A') ORDER BY receivedAt:u64 ASC` | `eq("threadId","thr-A")` | 2 rows, OK |
| f | blind index | `P AND senderHash = str('<hmac>')` | `eq("senderHash", h)` | 3 rows across both agents (the same sender), OK |
| g | count | raw `client.query(P.., {limit:1, count:true})` | `.withCount()` and `client.count().from(S).createdBy(W).where(..).fetch()` | 8 / 8 / 8 = expected 8 |

Offset paging: works, but the SDK warns pages shift if writes land between requests. Prefer the $key cursor for a stable crawl (only a stable order, not newest-first). For newest-first inbox UX, use offset, or cursor on receivedAt with `lt("receivedAt", u64(lastSeen))` (receivedAt ties would skip rows: add `$key` tiebreak client-side or accept second-resolution ties; untested). Raw responses return numbers as hex strings (`count`, `blockNumber`, u64 values). The raw `arkiv_query` attribute list is `[{name,type,value}]`.
A single ORDER BY key only, so no (receivedAt, $key) composite ordering.

## Poisoning (test 3)
Attacker tx `0x96e29a23497cb5ba19fcead488f6ce3dab0532a35ad4baf90ca5f427f3ca7c22` wrote 2 fully well-formed fake otp entities with the same schema name and `agentId = alex.t03.nanitecom.eth`, receivedAt = now (newer than all legitimate rows).
- Naive query (`P' AND agentId=alex AND type=otp ORDER BY receivedAt DESC LIMIT 5`, no creator): returned 2 attacker rows + 3 of 4 legit rows; the **latest-OTP query (c) returned the attacker's fake OTP**. This is the exact attack on the OTP flow.
- Add `$creator = addr(<writer>)`: 4 rows, 0 attacker rows. `$owner = addr(<writer>)` also excluded them in this test, but $owner is not safe as the pin once users own entities: an attacker can create an entity and `changeOwnership` it to the victim (untested, but `changeOwnership` has no recipient consent per SDK source). `$creator` is immutable. **Pin $creator.**
- Look-alike skipping (`.from(schema)` default `onMismatch: "skip"`): the attacker also wrote an entity with the right schema tag but only the `agentId` column. Builder returned the 2 well-formed fakes and `skipped: 1` (a **number**, not an array). With `onMismatch: "throw"`: `SchemaMismatchError: Column "type": entity 0x3255.. has no value for this required str column`. Conclusion: skip is a shape check only. It protects against malformed rows, not against forgery. A well-formed fake is indistinguishable by schema. Also note in throw mode a single malformed attacker row would make the whole query fail (DoS), so use skip plus $creator.
- Raw string queries without the schema tag still return all three attacker rows (tag `arkiv.schema` is just an attribute the attacker controls).
- Defence in depth to consider: reject rows whose `$creator` differs from the writer in the client even after the query (cheap), and keep the writer address in config, not read from chain.

## Latency (test 4)
Measured from the moment `createEntity` returned (SDK waits for the receipt) to the first successful read (polling every 250 ms, public RPC):

| run | getEntity | query by threadId+creator |
|---|---|---|
| 1 | 1286 ms | 2218 ms |
| 2 | 704 ms | 796 ms |
| 3 | 350 ms | 604 ms |

So entities are readable essentially at receipt (indexer lag below ~1-2 s, the first run included cold-connection time). Blocks are 2 s. A single `arkiv_query` round trip on the public endpoint takes about 1.0-1.7 s (see ms in results/W4.json).
`watchEntityEvents({onEntityCreated, pollingInterval: 500})`: run 1 notified 942 ms after the receipt returned; run 2 notified 2787 ms BEFORE createEntity returned to the caller (the SDK's receipt wait is slower than the event poll). So notifications arrive within roughly one block of inclusion. It filters nothing server-side: the callback gets every create on the registry, so filter by `owner` (the creator at create time) client-side. Expiry emits no event. Fine for a live inbox "new mail" nudge, then run the pinned query.

## Plaintext leakage (test 5)
What an outsider (anyone with the public RPC) learns from the attributes of an `nanite.email.v0` entity:

| Field | Learned | Severity | Mitigation |
|---|---|---|---|
| agentId (ENS name) | which agent received mail; links to ENS records, owner of the name, and the human-readable identity | Medium: "alex.acme.nanitecom.eth got N mails" is identity + volume | Opaque agentId = HMAC(secret, ens name) or a random per-agent id: removes the link and equals a per-agent pseudonym, but judges then cannot read the inbox by name, and clients need the id mapping (derivable from the agent seed). Recommend: demo schema keeps ENS name (readable, a stated tradeoff), production option keeps a per-agent opaque id. Keep both mapped in the Nanite API only. |
| ownerId (user wallet) | which wallet owns the agent: links all of a user's agents together, and links them to on-chain identity | High for privacy | Same: HMAC/pseudonymous owner id, or drop the column and rely on agent id. Not needed for the agent to read its own inbox; needed only for "all my mail" listing: a per-user derived id works equally well. |
| receivedAt | exact arrival second: activity patterns, timezone, bursts around sign-ups | Medium | Coarsen to a bucket (e.g. minute or hour) in the public column and keep the exact time inside the ciphertext. Ordering within a bucket then needs the decrypted time or $key. Hurts only ties. |
| type | otp vs conversation: reveals "this agent is signing in to something now" | Medium | Can't hide while expiry class differs (expiry is visible anyway via $expiresAt: 5-minute vs months tells the same thing). Accept and document. |
| threadId | conversation grouping and thread length; correlation across threads | Low-Medium | Make it an HMAC / random id per thread (never subject-derived). Already opaque in design. |
| senderHash | same sender produces the same hash forever: anyone can link mails from one sender across an agent AND across all agents using the same HMAC key; a dictionary attack on a guessable sender (known sender list) is possible if the HMAC key leaks, otherwise infeasible | Medium | Key the HMAC per agent or per user (HMAC(userKey, sender)) so no linkability across users; use the server secret only if cross-user lookup is never needed. Never use an unkeyed hash (email addresses are guessable). Keep the key out of Arkiv. |
| $creator / $owner / $expiresAt / $createdAt (block) | creator = Nanite writer (public anyway); expiry class; block-level timestamp (receipt time to ~2 s even if receivedAt is coarsened) | Low-Medium | $createdAt (block) leaks arrival time at 2 s resolution regardless: coarsening receivedAt alone does not hide it. Real mitigation is batching writes (delay/jitter). Document it. |
| keyId | key rotation version | Low | none needed |
| ciphertext size, wrappedKeys length | rough message size and number of readers (80 B per reader) | Low | pad ciphertext to size buckets |
| volume | entity counts per agent/day | Medium | inherent, state honestly |

Recommendation for the spike deliverable: keep ENS agentId and exact receivedAt (judge-readable, indexed filters work), state the tradeoffs in docs, and note the production variant (opaque agentId, per-user-keyed senderHash, bucketed receivedAt, batched writes).

## Schema change proposals
1. No change required to make queries work. All tested filters hit indexed columns.
2. Add a monotonic tiebreak/sort: receivedAt is second resolution, so same-second mails tie. Consider ms resolution (`u64` in ms): costless.
3. Add `schemaVersion` is already in the name (`nanite.email.v0`); keep it, and query only the exact current name.
4. Per-user keyed senderHash and (optionally) opaque agentId/ownerId per the leakage table.
5. Treat `ownerId` column as unauthenticated hint only (attacker can set any value); never trust it for authorization. Authorization is `$creator`.
6. Possibly drop `keyId` from the indexed set (not used in filters, leaks little but costs index space); minor.
7. Max 31 columns/32 attributes: current use is 10 plus the schema tag: ample headroom.
