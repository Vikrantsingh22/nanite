# W3: who writes Arkiv entities (ownership model)

Script: `scripts/arkiv/w3-ownership.ts`. Raw results with all tx hashes and keys: `results/W3.json`. Chain: Rabdi testnet, SDK 1.0.1. Operator = index 3 (0xA7B7...D247F), user = index 4 (0x5751...8186), derived writer = index 8 (0x2D2C...0E11). All results below were observed on-chain.

## Results by test

| Test | Result |
|---|---|
| A. Operator creates | `$creator = $owner = operator`. `.ownedBy(user)` does not return the key; `.createdBy(operator)` does. (Tx 0xa4e406cd...ab97, key 0x3f9e5fa3...85cd.) The `ownedBy(user)` count was 4 only because earlier B entities already belonged to the user. |
| B. Create + transfer in ONE tx | Works. `predictEntityKeys` matched the real keys. Single email: tx 0xba5a5062...63a6. Three emails in one batch: tx 0xb4a30310...e037, all three `$owner = user`, `$creator = operator`. `.ownedBy(user).createdBy(operator)` finds them. |
| C. After transfer | Operator patch, delete, extend and changeOwnership all FAIL (error `entity ... is owned by <user>, not <operator>`). User patch, extend and delete all succeed (txs in W3.json). |
| D. `permissionlessExtension` (0x02) + transfer | Operator CAN still extend after transfer (tx 0xc6a6ed91...b7db), but patch and delete still fail. This gives an operator-run retention job over user-owned mail with no other power. |
| E. Nonce race | See below. |
| F. Derived writer key | Writer (funded 0.05 tGLM by operator, tx 0xc2ee1686...455c) creates: `$creator = $owner = writer`. Writer can later `changeOwnership` to the user wallet (tx 0x5429bed0...1ba2). After that the writer cannot patch, the user can, and `$creator` stays the writer forever. |
| G. `readonly` (0x01) + transfer | Nobody can patch (error: "created readonly, so its contents can never change"). User extend and delete still work (txs in W3.json). |

### E: nonce race detail
- Key = keccak(chainId, 0x44..44, creator, nonce, salt). Creator nonce increments with every create by that account. An explicit salt does NOT remove the nonce dependence (same salt gives different keys at nonce 13 vs 14). With `NO_SALT` the key is just as nonce-dependent, merely guessable by others.
- E1 (stale prediction: predict, land another create from the operator, then send the batch): the whole batch REVERTED with `no entity 0x0864...4467`. Atomic: nothing created, nothing transferred, no wrong key moved. A stale prediction fails safe (the transfer references a key that does not exist). Cost is a failed tx.
- E2 (two concurrent batches, same prediction): one tx failed ("Execution error without revert data", same-account tx nonce collision or the stale prediction), one landed and was correctly owned by the user. The failed one created nothing.
- E4: three sequential batches, each re-predicting just before sending, all matched.
- Safe pattern: a per-operator-account serialized queue (one batch in flight; call `predictEntityKeys` immediately before send; on revert re-predict and retry). Alternatives: (a) a pool of N operator accounts, one queue each; (b) 2-step fallback: create batch, read `createdEntities`, then a second tx with `ownershipChanges` (no prediction at all, but a window where the operator owns the mail and 2 txs per batch). Batch several emails per tx to cut load.

## Comparison of the three writer models

| | 1. Operator-owned | 2. Operator creates then transfers to user (one batch) | 3. Derived per-user writer key |
|---|---|---|---|
| User ownership | None on-chain (`$owner` = operator). Ownership only via `ownerId` attribute, which is a claim. | Real: `$owner` = user wallet; only the user can patch, delete, extend (tested). `$creator` = operator (provenance). | Real after handover (`$owner` = user), but before handover the key holder (server) owns it. If never handed over, `$owner` = a derived key, not the user's wallet. |
| Gas payer | Operator | Operator | Operator must fund each writer key first (extra tx per user); writer then pays. User wallet pays only for its own later actions. |
| Txs per email | 1 (batchable) | 1 per batch of N emails (create + transfer in one tx) | 1 per email (or batch) if left writer-owned; +1 (or batched) changeOwnership to hand over; +1 funding per user |
| Retention (who can extend) | Operator, freely | User only. Operator can extend only if the entity was created with `permissionlessExtension` (tested, extend only). Otherwise the user must run extends, or the user gives the server a key. | Writer key holder (server holds it) until handover; afterwards user only (same permissionless option available) |
| Revocation | Operator can delete anything; user cannot revoke the operator | Complete: after the batch the operator has no write power (except optional extend). Delete is the user's. | Server retains power until handover; rotating or discarding the derived key revokes it |
| Failure modes | Operator key leak = all mail tamperable/deletable | Nonce race (fails safe, atomic revert); operator key leak cannot touch already-transferred mail, only affects in-flight creates and new mail | Funding failures; key derivation/custody complexity; writer out of gas; extra state per user; `$creator` still not the user |
| Demo ease | Easiest | Easy (about 15 lines, tested here); needs a serialized send queue | Hardest (key derivation, funding, handover flow) |
| Reads to judges as "you own your data" | Weak. Fails the claim | Strong. Query by `$owner = user` and show that the Nanite operator gets `owned by ...` errors on patch/delete | Medium. Works but story is convoluted ("the server holds your derived key") |

## RECOMMENDATION
Use model 2: the operator creates and transfers to the user wallet in one `executeBatch` (create with predicted salt + `ownershipChanges`). It is tested, one tx, gives real on-chain ownership that the operator cannot undo, and demos well ("the operator literally cannot delete your mail"). Details:
1. Serialize operator sends per account (single-flight queue); call `predictEntityKeys` right before sending; on revert re-predict and retry. A stale prediction reverts atomically and never transfers a wrong key.
2. Set `permissionlessExtension` on OTP and conversation mail so a server retention job can keep mail alive without ownership; or accept that the user's client extends. Do NOT set it if you want expiry strictly user-controlled.
3. Consider `readonly` for immutable mail records; but then grant changes via `wrappedKeys` patch (see schema) are impossible, so only use readonly if key grants live elsewhere.
4. Keep the `ownerId` attribute and always query with `.ownedBy(user).createdBy(operator)` to resist look-alike entities.
5. Skip model 3 for the hackathon; keep it as a fallback only if the user wallet cannot be known at delivery time (then create under a writer key and hand over later).
