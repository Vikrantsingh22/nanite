# W1: size and cost (Arkiv Rabdi testnet, wallet index 1)

Script: `scripts/arkiv/w1-size.ts` (phases t1, t1b, t1c, t2, t3, t4, t5, t6). Raw data: `docs/arkiv-spike/results/W1.json` (early failed attempts with wrong value types were deleted; some t4/t5 retries remain in it).
Gas price on Rabdi was a constant 1 gwei (`effectiveGasPrice` = 1,000,000,000), so cost in tGLM = gasUsed x 1e-9. Other bytes columns in all tests: wrappedKeys 160 B + nonce 12 B = 172 B. All entities used 1 hour expiry unless noted.

### T2 over-limit (SDK side)
- 131,073 total bytes across columns: `EntityTooLargeError` thrown client-side before send, as expected.
- One single bytes value of 131,073 B: `InvalidValueError` (per-value 128 KiB cap), also client-side.
- NOT checked: raw node behaviour via eth_estimateGas (skipped; see below, the node already rejects below the SDK limit).

### T5 round trip
64 KiB ciphertext created then read with `getEntity(key, EmailSchema)`: byte-exact match, `getEntity` took 495 ms; entity was visible on the public RPC ~0.7 s after the receipt. Note the returned bytes column is `{type, value}`-shaped (see friction file), not a bare Uint8Array. The 128 KiB-class entity was not read back (64 KiB only).

### T6 expiry
Cost depends on expiry length: +134,182 gas for 30 days vs 1 hour on a 4 KiB entity (+47%). Slope ~0.1035 gas per block (30 d = 1,296,000 blocks at 2 s), so max 91 days (7,884,000 blocks) would add roughly 0.8M gas (~0.0008 tGLM). Not verified whether the expiry term scales with entity size.

## Cost model
gas ~ 164,000 + ~40 gas per payload byte (+ ~0.1 gas per block of lifetime). 64 KiB to 128 KiB is ~5.2M gas, well under the 2^24 cap; size is not the binding limit, the transaction size is.

## Per 1,000 emails and faucet coverage
- Typical email (24.6 KiB), 1 h expiry: 1.043 tGLM per 1,000 emails singly; 1.027 per 1,000 batched (4 per tx, only 1.5% saving).
- Small email (~6 KiB): ~0.33 tGLM per 1,000 batched.
- Add the expiry term for real retention: 30 days adds ~0.134 tGLM per 1,000 emails (4 KiB reference; estimate).
- Wallet funded with 1.5 tGLM covers about 1,430 typical emails at 1 h expiry (about 1,270 at 30 d). I used 0.061 tGLM for the whole spike (1.439 left).

## Conclusions for Nanite
1. A typical email (~25 KiB ciphertext) fits easily: ~1.0M gas, ~0.001 tGLM, one tx.
2. The real hard limit is NOT 128 KiB of bytes: the chain rejects the tx ("Execution error without revert data", no revert reason) at roughly 128,2xx bytes of ciphertext with 172 B of other columns, i.e. about 2.7 KB less than the SDK's `MAX_ENTITY_BYTES`. Likely the node's ~128 KiB transaction size limit including ABI overhead (hypothesis, not confirmed). Treat the ceiling as ~125 KiB of total bytes columns per entity to leave margin; the SDK check passes sizes that then fail on chain and wastes the retry plus gas estimate.
3. executeBatch is bounded by the same whole-tx size: 4 typical emails ok, 5 not; 10 small ok, 25 small not. Batching saves almost nothing in gas (~1.5%), so batch only for atomicity (create + changeOwnership) or fewer round trips, not for cost. Keep batches under ~100 KiB payload.
4. Above ~125 KiB (large attachments): chunk ciphertext across several entities (e.g. 100 KiB chunks) linked by a shared `threadId`/message id plus an index column (add `chunkIndex u64 indexed` and `parentKey key`), with a manifest entity holding wrappedKeys and chunk count; or store the blob on Swarm/IPFS and keep only the reference + hash in the entity. Chunking costs the same ~40 gas/byte on chain, so a 10 MB attachment would be ~400M gas (~0.4 tGLM) on-chain: for big attachments an external store is far cheaper. Not tested here.
5. Cost scales with both payload size and lifetime; budget the retention class (otp minutes vs conversation months) when estimating.
