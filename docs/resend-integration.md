# Resend integration: feasibility, setup, gaps, live test plan

Research date 2026-11-06 (task M1). Based on the Resend docs only; no API call to Resend was made. Anything marked UNVERIFIED must be confirmed in the live test (section 7).

## 1. Verdict

**Feasible, with one real constraint: the free-tier quota.**

- Receiving for arbitrary per-agent addresses on one domain works: once the domain's receiving MX record is verified, Resend accepts mail for ANY address at that domain (no per-address setup, no mailbox creation). Our router (`findMailboxByAddress`) then decides which addresses are real and drops the rest.
- Sending from any address at a verified domain works with no per-address setup ("you can send from any email address at that domain").
- Inbound has been generally available since Nov 3, 2025 (Resend blog "Inbound Emails"). No beta caveat found.
- Free plan: 3,000 emails/month, **100/day**, 3 domains, **1 webhook endpoint**, 30-day data retention.

**Blockers / hard constraints**

1. **Received mail counts against the quota.** Pricing FAQ: "Each received email counts towards your transactional emails quota." The errors page for `daily_quota_exceeded` (429): "Sent and received emails both count." The 100/day is shared by sent + received, and every message to ANY address at the domain counts, including spam to non-existent agents. Anyone can burn the daily quota by mailing random addresses. This is a demo-day risk, not a blocker. Mitigation: Pro ($20/mo, 50k/mo) on demo day, or keep the address private.
2. **Over quota, received content is lost.** Error `403 email_above_quota`: "Email content can't be retrieved because it was over quota when received." So after ~100 mails/day the `email.received` webhook may still arrive but `GET /emails/receiving/{id}` fails and the mail is unrecoverable (until upgrade).
3. **Only 1 webhook endpoint on free.** Local dev (tunnel URL) and production cannot both be registered. Plan to repoint the single webhook (or use the API `POST/PATCH /webhooks`), or pay.
4. **The API key used by our server must be Full access**, not Sending access: `sending_access` keys can only send and get `401 restricted_api_key` on the receiving API. A domain-scoped key is only possible with `sending_access`, so it cannot be used for fetching received mail.

## 2. DNS: use a subdomain

Recommendation: add **`mail.<domain>`** (any name, e.g. `mail`) in Resend, NOT the root domain. Reasons:

- Resend's docs: if the domain already has MX records, put Resend's MX on a subdomain. Two sets of MX records on one name lead to lost mail or hijacked mail (the lowest priority number wins; equal priority is unpredictable). Vikrant's root-domain mail stays untouched.
- Resend recommends sending from subdomains to isolate sender reputation.
- Our mailbox addresses become `<agent>.<user>@mail.<domain>` (set `SHARED_MAIL_DOMAIN=mail.<domain>`; see gap G9).
- A subdomain probably uses one of the 3 free domain slots (the status doc also lists this as unverified: check with `resend usage`).

Records to add at the DNS host of `<domain>`. **Do not type values by hand: copy them from the domain's Records tab in the Resend dashboard** (Resend says they "must match exactly what Resend generated"). Names below are relative to the zone for `<domain>` when the domain added in Resend is `mail.<domain>`:

| Purpose | Type | Name (host) | Value source | Notes |
|---|---|---|---|---|
| DKIM | TXT | `resend._domainkey.mail` | Records tab (long `p=...` key) | Needed for sending (and keep even if receive-only) |
| SPF (envelope / Return-Path) | TXT | `send.mail` | Records tab (`v=spf1 include:amazonses.com ~all` style) | Return-Path subdomain defaults to `send`; fixed at creation, cannot be changed later |
| Bounce / feedback | MX | `send.mail` | Records tab, priority from the tab | For bounces; part of "sending" records |
| **Receiving** | MX | `mail` (the domain itself) | Records tab, shown after enabling Receiving (e.g. `inbound-smtp.<region>.amazonaws.com` or `receive*.forge.rmta.net`) | Must have the LOWEST priority on that name; put nothing else there. Host name and priority are not in the docs: copy from the dashboard |
| DMARC (optional but recommended) | TXT | `_dmarc.mail` | Self-written, e.g. `v=DMARC1; p=none; rua=mailto:<vikrant's address>` | Not generated by Resend; Resend has a DMARC guide/analyzer |
| Tracking CNAME | none | - | - | Leave open/click tracking OFF (transactional, and agents read plain text) |

Notes:
- If the DNS host proxies (Cloudflare orange cloud), set Resend CNAMEs to DNS-only (not applicable if records are TXT/MX).
- Verification usually completes within ~15 min; DNS may take up to 72 h. "Restart verification" in the dashboard after that. Check with dns.email.
- The exact region is a choice at creation (`us-east-1` default, `eu-west-1`, `sa-east-1`, `ap-northeast-1`); pick the closest to the recipients. The region also appears to change the receiving MX hostname (`receive-euw1...` variant).
- Do NOT touch the root-domain MX, SPF or DKIM.

## 3. Dashboard steps (Vikrant)

1. resend.com -> Domains -> Add Domain. Name: `mail.<domain>`. Region: nearest. Leave tracking off, TLS opportunistic (or enforced if you like; enforced refuses recipients without TLS). Leave Return-Path as `send`.
2. Copy the DKIM and SPF records from the Records tab into the DNS host. Click Verify.
3. On the domain page, switch **Enable Receiving** on (a modal shows the MX record). Add it, click "I've added the record", wait until the receiving record shows verified. Only the MX is verified in this step.
4. Webhooks -> Add Webhook. Endpoint: `https://<public-host>/webhooks/resend`. Events: `email.received` only (our pipeline ignores everything else, and extra events only waste retries). Save, then copy the signing secret (`whsec_...`) from the webhook detail page.
5. API Keys -> Create. Permission **Full access** (needed for the receiving API). Domain restriction is not available for full access. Name it e.g. `nanite-server`.
6. Put `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`, `SHARED_MAIL_DOMAIN=mail.<domain>` into the local `.env` (never into chat).

Equivalent API calls (for later automation): `POST /domains` (`name`, `region`, `capabilities: {sending, receiving}`), `POST /domains/{id}/verify`, `POST /webhooks` (`endpoint`, `events`; the response contains `signing_secret`). The get/list/update domain pages were not retrievable via fetch; they exist in the API reference.

Quick no-DNS inbound smoke test: every account also has a Resend-managed `<id>.resend.app` receiving domain (Emails -> Receiving tab -> three dots -> Receiving address). Any local part works there. This is useful to prove the webhook and fetch path before DNS propagates (create a mailbox row on that domain, i.e. `SHARED_MAIL_DOMAIN=<id>.resend.app`). Sending from it is not documented; do not rely on it.

## 4. Getting real webhooks into the local Docker API

The API listens on 127.0.0.1:4000 only. Resend needs a public HTTPS URL. Everything must run in Docker.

| Option | How | Pros / cons |
|---|---|---|
| **A. cloudflared quick tunnel (recommended)** | Add a compose service (profile `tunnel`) using image `cloudflare/cloudflared:<pinned>` with `tunnel --no-autoupdate --url http://api:4000`. The log prints a random `https://<x>.trycloudflare.com`. | No account, no install on the host, free. URL changes on every restart, so you must edit the Resend webhook URL each time (1-endpoint limit makes this a manual `PATCH /webhooks/{id}`). Pin the image tag (project rule). |
| B. cloudflared named tunnel | Same image with a token from a free Cloudflare account and a stable hostname such as `dev-hook.<domain>` | Stable URL, no webhook edits. Needs the domain's DNS on Cloudflare (or a CNAME) - touches Vikrant's DNS. |
| C. ngrok | `ngrok/ngrok` image with an authtoken | Works; free plan gives one static dev domain. Needs an account and a token in `.env`. |
| D. Temporary public deploy | Lightsail + Caddy (T4.3) | Most realistic but is the full deploy task; do after the local proof. |

**Start the tunnel (option A, already in `docker-compose.yml`, profile `tunnel`, image `cloudflare/cloudflared:2026.10.2`):**

```
docker compose up -d db api                                   # the api must be up first
docker compose --profile tunnel up -d tunnel && docker compose logs tunnel | grep trycloudflare
# -> https://<random>.trycloudflare.com ; webhook endpoint = <that URL>/webhooks/resend
docker compose --profile tunnel stop tunnel                   # stop it after the test (it exposes ALL api routes)
```

The URL changes on every start; repoint the single Resend webhook (dashboard, or `PATCH /webhooks/{id}`) each time. If the log is empty, wait a few seconds and run the second command again.

Recommendation: **A for the first live test**, then D (T4.3) for the permanent webhook. Only expose `/webhooks/resend`; the tunnel forwards everything to the API, so the other `/v1/*` routes are public while it is up (they need tokens, but keep the session short). A Caddy/`--url` path filter is not available in quick tunnels, so stop the tunnel after the test.

Resend retries failed deliveries (immediately, 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 10 h) and disables an endpoint that keeps failing; a dead tunnel therefore pauses the webhook until re-enabled on the Webhooks page. Failed or succeeded messages can be replayed from the dashboard (our dedupe makes replays safe). No IP allowlist is published; rely on the Svix signature.

### 5d. Message-ID replacement, signature v3 and threading (R1, 2026-11-06)

- Proof the v2 signature itself was genuine: the sent copy of the first real reply was decrypted in memory and verified against LIVE ENS twice. With our original Message-ID: `valid: true`, signer `0x4EA6...7Ae6`. With the delivered SES Message-ID: `signer_mismatch`. So only the signed Message-ID line was wrong, not the signature.
- v3: canonical string `nanite-send-v3\n<ens>\n<from>\n<to>\n<sha256(subject)>\n<sha256(body)>\n<date>\n<x-nanite-message-id>`; headers `X-Nanite-Agent`, `X-Nanite-Date`, `X-Nanite-Message-Id: <sendLogId@domain>`, `X-Nanite-Sig-Version: 3`, `X-Nanite-Signature`. We no longer set `Message-ID`. The verifier handles v3 (default) and legacy v2 (uses `Message-ID`; it fails on Resend-delivered mail and the verdict then carries a `hint` saying so).
- Threading of replies TO the agent: the real Message-ID is only known to the provider. After a successful send the API calls `GET /emails/{id}` (`message_id`; up to 4 tries within 3 s, best effort, never fails the send) BEFORE writing the sent copy, and stores it as `meta.messageId` (our id is `meta.naniteMessageId`). The sent copy's `threadId` is `threadIdForRoot(root)` with the same HMAC the inbound pipeline uses, where root = first `References` id of the mail answered, else the provider id. A user's reply to our mail carries that id in `In-Reply-To`/`References`, so the inbound pipeline (unchanged) computes the same `threadId` with no new attribute. Limits: (1) if the lookup fails or times out the copy has no `messageId` and keeps its own opaque thread (replies then thread as a new conversation, and replying to that sent copy via `inReplyTo` goes out unthreaded); (2) the link is the shared `threadId` only, there is no index from Message-ID to entity; (3) a client that drops both `In-Reply-To` and `References` cannot be linked; (4) self-custody agents' replies have no In-Reply-To headers anyway (the server cannot decrypt the source), so their fresh sent mails link by provider id only.

### 5e. User domains: the onboarding domain flow (T3.6)

Every user adds their own mail domain in onboarding step 04. Code: `apps/api/src/domains/*`, `apps/api/src/routes/domains.ts`; table `user_domains` (migration `0003`); UI `apps/web/src/components/onboarding/domain-step.tsx`.

- **Create:** `POST /onboarding/domain {name, region?}` normalizes the name (lowercase, strips scheme/path/port/trailing dot), refuses the platform domain `nanitecom.itsvikrant.tech` and its subdomains (`400 domain_reserved`) and names used by another account (`409 domain_taken`), then lists the Resend account's domains: an existing one with that name is adopted, otherwise `POST /domains` creates it (`capabilities` sending + receiving enabled, `open_tracking` and `click_tracking` false, `tls: opportunistic`, region `RESEND_DEFAULT_REGION`, default `ap-northeast-1`). Idempotent per user and name. Errors: domain limit reached (plan has no free slot; `403` with a limit message from Resend) -> `409 domain_limit_reached`; invalid -> `400`; key/permission -> `503 resend_not_configured`; anything else -> `502 resend_unavailable`. The free plan has 3 slots (1 used by the platform domain).
- **Records:** stored as Resend returned them (`records` jsonb). The view gives each record's host relative to the zone root (registrable domain: last two labels, or three under `co.uk`, `co.in`, `com.au` and similar), for example `send.nanitecom` in zone `itsvikrant.tech`, plus `fqdn`, `value` (Resend's surrounding quotes removed), `priority`, `resendStatus` and `dnsFound`.
- **Our DNS check:** Cloudflare DNS over HTTPS (`application/dns-json`) through an injectable resolver. TXT must contain the expected value (split TXT strings are joined), CNAME and MX must point at the expected host. `dnsFound` is `null` when the lookup failed. The result is stored in `dns_check` with the detected DNS provider (from the root's NS records: Cloudflare, GoDaddy, Namecheap, Route 53, Google, other) that selects the tips shown.
- **Verify:** when every record has first been found, Nanite calls `POST /domains/{id}/verify` itself (again every 10 minutes while Resend still reports `not_started`/`failed`/`temporary_failure`). `POST /onboarding/domain/verify` does a check plus a verify on demand, at most once per 30 s per domain (`429 verify_rate_limited` with `retryAfterSeconds`).
- **Background verifier (one in-process loop, ticks every 5 s, state only in Postgres):** for every unverified domain, a full check (`GET /domains/{id}` + DNS lookups) when due: every 15 s for the first 10 minutes after creation or the last verify request, every 2 minutes up to 2 hours, every 15 minutes up to 72 hours, then it stops (status stays; pressing Check now restarts the clock).
- **Webhook events:** `/webhooks/resend` (same Svix check) also handles `domain.created`, `domain.updated`, `domain.deleted`: the matching row is updated from the payload (`data.id`, `status`, `records`), or refetched with `GET /domains/{id}` when the payload is partial; `domain.deleted` removes an unverified row and marks a verified one `failed`. `email.received` handling is unchanged. Add the events to the existing webhook with `apps/api/scripts/resend-webhook-domain-events.ts --id=<webhook id> [--apply]` (`PATCH /webhooks/{id}` with the full `events` list; dry run by default). Not run yet.
- **Optional (Vikrant, revised 2026-11-06):** the domain is never forced. Wizard step 04 offers "Use your own domain" (recommended; DNS can take up to 72 hours) or "Start now" with the shared domain. `POST /onboarding/complete` never needs a verified domain. `POST /agents` creates the mailbox and the ENS `email` record `<agent>@<user domain>` only while the user's domain is verified; otherwise `<agent>.<user>@SHARED_MAIL_DOMAIN`, never a 409. Existing agents keep their address when a domain verifies later (no migration of old agents; the old address keeps routing). Inbound routing is by mailbox address, so mail to any verified user domain routes and unknown addresses are dropped. Verification continues in the background after onboarding is finished, and the dashboard "Mail domain" card lets a user add a domain later. The Resend free-plan limit (3 domains) only affects users who opt in.
- **Delete:** `DELETE /onboarding/domain` only while unverified: frees the Resend slot and the local row.

### 5b. Webhook latency

Before (sync, real Arkiv writer, `send-fake-webhook.ts` against the dev stack, 2026-11-06): `POST /webhooks/resend` took 7,590 ms (access log `ms`). After: 16 ms for the request (same script, same real Arkiv write, which now finishes about 7 s later in the background and logs `stored`). The request does verify + one insert + routing + queued ledger rows, no provider or Arkiv call. A restarted API re-processes events left `received`, `processing` or `failed` (startup sweep, then every minute; stale `processing` after 5 minutes, bounded to 5 attempts, then parked as `failed`/`attempts_exhausted`). Because the webhook is answered before processing, Resend no longer retries a failed event: the sweep does.

## 8. Open questions and risks

1. ~~Does Resend preserve a custom `Message-ID`?~~ No (Resend/SES replace it); resolved by signature v3, see 5d.
2. Receiving MX host name and priority are not in the public docs (only in the dashboard). Whether a subdomain consumes a domain slot is unconfirmed (the 3-domain free limit leaves room either way).
3. Does the daily 100 count mail to non-existent addresses and spam? The docs say all received mail counts. Abuse risk for a public demo address; also catch-all can not be disabled (any local part is accepted).
4. Webhook timeout length is not documented; synchronous Arkiv writes may exceed it. Mitigation is already idempotent retries; if it bites, acknowledge first and process async (queue).
5. 1 webhook endpoint on free: dev tunnel and production exclude each other. Option: deploy first (T4.3) and develop against fake events, or pay for Pro on demo day.
6. `email_above_quota` makes over-quota mail unrecoverable; consider a mail-side notice or upgrading before the demo.
7. Spam/phishing and prompt-injection content in inbound mail: already treated as untrusted (`content_trust`); unchanged by this integration.
8. Resend-managed `<id>.resend.app` domain: sending from it is undocumented; for sending a verified own domain is required (`403 validation_error` otherwise).
9. API reference pages for get/list/update domain and the attachments endpoint were not retrievable as text in this pass; names above for those come from the docs index only.
